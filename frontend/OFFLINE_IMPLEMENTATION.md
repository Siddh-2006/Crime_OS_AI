# Offline-First Implementation Guide

This document describes the offline-first architecture implemented in Crime OS.

## Overview

Crime OS now supports offline access for police officers, allowing them to:
- View cached case data when offline
- Make updates that automatically sync when connection is restored
- Track sync status in real-time
- Download evidence files for offline viewing

## Architecture

### Core Components

1. **IndexedDB Storage (Dexie.js)**
   - `cases`: Stores cached case data (5 most recent per officer)
   - `outbox`: Queues pending mutations for sync
   - `metadata`: Tracks sync timestamps and state

2. **Cache Manager** (`CaseCacheManager`)
   - LRU eviction (keeps 5 most recent cases per officer)
   - Automatic cache updates on online access
   - Per-officer isolation

3. **Outbox Manager** (`OutboxManager`)
   - Queues POST/PUT/PATCH/DELETE operations when offline
   - Respects operation dependencies
   - Automatic retry with exponential backoff

4. **Sync Manager** (`SyncManager`)
   - Monitors online/offline status
   - Automatic sync on connection restore
   - Real-time sync state notifications

5. **Offline API Client** (`OfflineApiClient`)
   - Transparent fallback to cache when offline
   - Automatic queueing of mutations
   - Compatible with existing `apiClient` usage

## Usage

### 1. Fetching Case Data with Offline Support

Use the `useCaseData` hook instead of manual API calls:

```tsx
import { useCaseData } from '@/hooks/useCaseData';
import { useAuth } from '@/hooks/useAuth';

function CaseComponent({ caseId }: { caseId: string }) {
  const { user } = useAuth();
  const {
    snapshot,
    checklist,
    participants,
    loading,
    error,
    isOffline,
    isCached,
    refetch,
  } = useCaseData(caseId, user?._id || '');

  // Data automatically comes from cache when offline
  // Refetch will update cache when online
}
```

### 2. Making Offline-Aware Mutations

Use the offline helper functions:

```tsx
import { offlinePost, offlinePut, getQueuedMessage } from '@/lib/offline/offlineHelpers';

async function updateParticipant(caseId: string, participantId: string, data: any) {
  const result = await offlinePut(
    `/cases/${caseId}/participants/${participantId}`,
    data,
    {
      affectedFields: ['participants'], // For field-level LWW
    }
  );

  if (result.queued) {
    alert(getQueuedMessage(true)); // "Operation saved and will sync when online"
  } else {
    alert('Updated successfully');
  }
}
```

### 3. Monitoring Sync Status

Use the `useSync` hook:

```tsx
import { useSync } from '@/hooks/useSync';

function SyncComponent() {
  const { status, isOnline, pendingCount, triggerSync } = useSync();

  return (
    <div>
      Status: {status}
      {pendingCount > 0 && (
        <button onClick={triggerSync}>
          Sync {pendingCount} pending operations
        </button>
      )}
    </div>
  );
}
```

### 4. Handling Dependencies Between Operations

When one operation depends on another (e.g., create participant → attach sections):

```tsx
import { OutboxManager } from '@/lib/offline';

// First operation
const createOpId = await OutboxManager.queueMutation(officerId, caseId, {
  method: 'POST',
  endpoint: `/cases/${caseId}/participants`,
  payload: participantData,
  affected_fields: ['participants'],
});

// Dependent operation
await OutboxManager.queueMutation(officerId, caseId, {
  method: 'POST',
  endpoint: `/cases/${caseId}/participants/${participantId}/sections`,
  payload: sectionData,
  affected_fields: ['participants'],
  depends_on: createOpId, // This ensures correct ordering
});
```

## Field-Level Last-Write-Wins

The system implements field-level LWW conflict resolution:

1. **Independent Fields**: Updates to different fields don't conflict
   - Updating `case.title` and adding a `diary entry` are independent
   - Both succeed without overwriting each other

2. **Same Field**: Last write wins based on timestamp
   - Two officers updating the same participant field
   - Server timestamp determines the winner

3. **Metadata**: Each cached case has:
   - `version`: Incremented on each update
   - `last_synced`: Timestamp of last successful sync
   - `last_accessed`: For LRU eviction

## Cache Eviction

- **Per Officer**: Each officer has independent cache
- **Limit**: 5 most recently accessed cases
- **LRU**: Least Recently Used cases evicted first
- **On Access**: `last_accessed` timestamp updated on every view
- **Manual Clear**: All caches cleared on logout

## Sync Behavior

### Automatic Sync Triggers
1. Connection restored (`online` event)
2. Page load (if pending operations exist)
3. After queueing new operation (checks if online)

### Manual Sync
- Click sync indicator in navbar
- Call `SyncManager.syncAll()`

### Sync Process
1. Fetch pending operations ordered by timestamp
2. Respect dependency chains (`depends_on`)
3. Execute each operation sequentially
4. Update status: `pending` → `succeeded` or `failed`
5. Remove succeeded operations
6. Retry failed operations (max 3 attempts)

### Sync Failures
- Operations marked as `failed` after 3 retries
- User can manually retry via sync indicator
- Last error message stored for debugging

## Evidence Files

Evidence files are handled separately:

1. **URLs Always Cached**: Cloudinary URLs stored in cache
2. **Manual Download**: User can download files via `OfflineEvidenceManager`
3. **Browser Downloads**: Files saved to device's download folder
4. **No Automatic Download**: Large files not cached by default

## Integration with Existing Code

### Minimal Changes Required

The offline system is designed to integrate with minimal changes to existing code:

1. **Wrap workspace with `OfflineWorkspaceWrapper`**:
   ```tsx
   // Before
   <InvestigationWorkspace caseId={caseId} />
   
   // After
   <OfflineWorkspaceWrapper caseId={caseId} />
   ```

2. **Replace direct API calls with offline helpers**:
   ```tsx
   // Before
   await apiClient.post(`/cases/${caseId}/participants`, data);
   
   // After
   await offlinePost(`/cases/${caseId}/participants`, data, {
     affectedFields: ['participants'],
   });
   ```

3. **Use hooks for data fetching**:
   ```tsx
   // Before
   const [data, setData] = useState(null);
   useEffect(() => {
     apiClient.get('/cases/123/participants').then(res => setData(res.data));
   }, []);
   
   // After
   const { participants } = useCaseData('123', officerId);
   ```

## Performance Considerations

1. **Cache Size**: Limited to 5 cases per officer (~5-10MB typically)
2. **IndexedDB**: Asynchronous, doesn't block UI
3. **Sync**: Processes operations sequentially to maintain order
4. **Memory**: Case data kept in React state, not duplicated

## Security

1. **Per-Officer Isolation**: Each officer's cache is separate
2. **Clear on Logout**: All offline data deleted on logout
3. **No Token Storage**: JWT tokens remain in localStorage (existing behavior)
4. **Refresh Handling**: Existing token refresh mechanism unchanged

## Troubleshooting

### Cache Not Working
```tsx
import { CaseCacheManager } from '@/lib/offline';

// Check if case is cached
const isCached = await CaseCacheManager.isCaseCached(caseId, officerId);
console.log('Is cached:', isCached);

// Get cache status
const status = await CaseCacheManager.getSyncStatus(caseId);
console.log('Cache status:', status);
```

### Outbox Not Syncing
```tsx
import { OutboxManager } from '@/lib/offline';

// Check pending operations
const pending = await OutboxManager.getPendingOperations(officerId);
console.log('Pending:', pending);

// Check failed operations
const failed = await OutboxManager.getFailedOperations(officerId);
console.log('Failed:', failed);

// Manually retry
await OutboxManager.retryOperation(operationId);
```

### Clear Everything
```tsx
import { db } from '@/lib/offline';

// Nuclear option - clear all offline data
await db.delete();
await db.open();
```
